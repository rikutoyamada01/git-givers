# **5\. 機能詳細・ロジック設計 (Logic Details)**

## **5.1. Owner制限 & 自作自演防止 (Anti-Gaming)**

「他者への貢献」のみを評価するため、以下の制限をシステムレベルで適用する。

### **5.1.1. 表示・Assign制限**

* **レコメンド除外**: Issue.ownerId \== CurrentUser.id の場合、APIレスポンスのリストから除外する。自分のおすすめに自分のIssueは出ない。  
* **Assign制限**: GitHub側でOwner自身がAssignされた場合、GitKarma上では「対応中」ステータスにするが、**Karma付与対象フラグはFalse**にする。

### **5.1.2. 報酬制限**

* **No Self-Karma**: Issue解決時、AssigneeId \== RepositoryOwnerId の場合、**Karma報酬（Base, Boost含む全て）は 0 になる。**  
* **No Self-Tip**: 自分のリポジトリに対するコメントやレビューに対しても、Action Based Karmaは発生しない。  
  * *理由: Ownerにとっての報酬は「コードが書かれたこと」そのものであるため。*

## **5.2. Today's 0-star Pickup (System Boost)**

孤独な開発者を救うための日替わり自動選出ロジック。

### **5.2.1. 選出基準**

毎日0時にバッチ処理、またはアクセス時に動的に以下の条件で1〜3つのリポジトリを選出する。

1. **Star Count**: 0 (厳密に0、または極小) であること。  
2. **Activity**: 直近1週間以内にコミットまたはIssue更新があること（放置リポジトリではない）。  
3. **Boost**: まだユーザーからのBoostを受けていない（発見されていない）こと。

### **5.2.2. 効果**

* **システムブースト**: 選出されたIssueには、システム側から仮想的に「大量のBoost（例: \+10,000pt相当）」がかかった状態として扱う。  
* **UI優先表示**: ダッシュボードの最上段に固定表示される。  
* **特別報酬**: このPickup枠から解決された場合、通常よりも高い倍率（M\_{pickup}）のKarmaが付与される。

## **5.3. Karma算出ロジック (改定版)**

### **5.3.1. 算出式**

* **M\_{discovery} (発見係数)**:  
  * Star数 S に反比例する。  
  * S=0 \\rightarrow \\times 3.0 (最大)  
  *   
  *   
  * S \\ge 1000 \\rightarrow \\times 1.0 (等倍)

これにより、**「人気リポジトリの簡単なバグ修正」よりも「無名リポジトリのバグ修正」の方が圧倒的に稼げる**バランスにする。

### **5.3.2. Contribution Logの生成**

Issue Closeイベント処理の最後に、以下の処理を行う。

1. Karma計算。  
2. UsersテーブルのKarma更新。  
3. **ContributionLogsテーブルへInsert**（タイトル、獲得ポイント、日時）。  
4. IssuesテーブルからDelete。

これにより、Issue自体は消えても「誰が何を解決して何点貰ったか」の事実は残り続ける。
